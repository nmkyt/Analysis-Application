# Тесты

73 юнит-теста на pytest в папке [`tests/`](../tests). Запуск:

```bash
.venv/Scripts/python -m pip install -e ".[dev]"
python -m pytest
```

## Принципы

### Без базы и без датасета

Тесты не требуют PostgreSQL и файлов `data/`. Вместо них — маленький искусственный `DemandData`
из [`tests/data.py`](../tests/data.py): две базы, три позиции, 85 недель. В нём явно заложены
все случаи, которые должна правильно обработать предобработка:

| Случай | Как задан |
|---|---|
| позиция выводится из ассортимента | позиция 3 выводится в среду 15.01.2025 |
| позиция появляется на базе позже начала данных | позиция 2 на базе 2 — с 06.03.2024 |
| база закрыта | база 2 без продаж в недели 20–23 |
| недели без продаж | каждая третья неделя ряда — ноль |
| разные единицы и вес | метры, штуки, листы с разным `kg_per_unit` |

**Почему.** Тест, которому нужна база, не запустится у проверяющего и в CI. А на полном
датасете ответ заранее неизвестен: нельзя сказать, сколько строк должно быть в панели,
не повторив тот же расчёт. На маленьких данных ожидаемый результат можно вывести вручную —
например, «последняя неделя ряда, выведенного в среду 15.01.2025, — неделя с 13.01».

### Проверяется смысл, а не реализация

Тесты сформулированы как свойства, которые должны выполняться при любой реализации:
«признаки не видят будущего», «закрытая неделя не попадает в обучение»,
«ряд с вдвое большей историей получает вдвое больший прогноз». Поэтому код можно
переписывать, не трогая тесты.

### Отсутствие утечки будущего

Самый важный тест — `test_features_do_not_see_the_future`. Продажи одной недели *T* умножаются
на 100, после чего выборка строится заново. Признаки всех строк с целевой неделей
раньше *T* + *h* обязаны совпасть с исходными, а признаки более поздних строк — измениться.

**Почему так, а не проверкой формул.** Утечка обычно возникает не в формуле лага, а в мелочах:
окно скользящего среднего, захватившее текущую неделю, сдвиг не в ту сторону, сортировка,
перепутавшая недели. Тест «изменили прошлое — посмотрели, что поменялось» ловит любую из них,
не зная, как именно устроены признаки. Он запускается для горизонтов 1 и 3.

Рядом — тесты, что лаг *h* действительно равен продажам недели *T* − *h*, а скользящее среднее
за 4 недели при *h* = 2 считается по неделям *T* − 5 … *T* − 2.

### Панель

Границы рядов (позднее появление, вывод из ассортимента), только полные недели, нули в неделях
без продаж, NaN в закрытых неделях, суммирование дневных продаж в недельные, будущие недели
с неизвестными продажами, и то, что добавление будущих недель не меняет обучающую выборку.

### Метрики

`evaluate()` сверяется с примером, посчитанным вручную: факт [0, 2, 4], прогноз [1, 2, 2],
вес единицы [1, 1, 0,5] → в килограммах ошибка [1, 0, −1], MAE = 2/3, WAPE = 0,5, bias = 0.
Отдельно — знак смещения, идеальный прогноз и вырожденные случаи: при нулевых продажах WAPE
и bias не определены (NaN, а не деление на ноль), при постоянных продажах не определён R².

**Почему вручную.** Метрики — то, по чему делается вывод о модели. Ошибка в формуле
незаметна (числа остаются правдоподобными), и проверить её можно только на примере
с заранее известным ответом.

### Модель

- прогноз неотрицательный;
- коды категорий при прогнозе совпадают с обучением, даже если категории пришли в другом порядке —
  иначе модель молча путала бы форматы баз;
- прогноз масштабируется вместе с историей ряда — проверка нормировки;
- разбиение по времени: части не пересекаются и идут по порядку;
- сохранение и загрузка дают ту же модель и те же прогнозы;
- при истории короче года обучение останавливается с понятной ошибкой, а не падает внутри
  scikit-learn.

### API

Через `TestClient` FastAPI, с подменой источников данных: база «недоступна», датасет —
тот же искусственный `DemandData`. Проверяется полный сценарий «обучить → дождаться задачи →
спрогнозировать → прочитать с фильтрами», коды 404, 409, 422 и 503, сообщение об ошибке
упавшей задачи и то, что два обучения одновременно не запускаются.

## Что не покрыто и почему

| Не покрыто | Почему |
|---|---|
| `connect()`, `create_database()`, `create_tables()`, `load_demand_data()`, `export_dataset()` | нужен работающий PostgreSQL. Это интеграционные тесты, а не юнит-тесты. Соответствие базы и датасета проверено вручную: `load_demand_data()` и `load_demand_data_csv()` дают одинаковый `DemandData` |
| графики `report.py` | результат — картинка, её проверяет человек |
| качество модели на полном датасете | это эксперимент, а не тест: метрики меняются при изменении признаков, и тест с порогом качества пришлось бы постоянно править |

Скорость: бустинг в тестах обучается на 30 итерациях, поэтому весь набор проходит меньше
чем за минуту.
