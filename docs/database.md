# База данных

Учётная система сети металлобаз в PostgreSQL 15+.

## Развёртывание

Параметры подключения берутся из `.env` (шаблон — `.env.example`).

**1. Сервер, роль и база** — один из двух вариантов:

```bash
docker compose --env-file .env -f infra/docker-compose.yml up -d   # PostgreSQL 17 в контейнере
python -m sales_analytics.storage init                             # или на установленном PostgreSQL
```

В контейнере роль и база создаются при первом запуске. На установленном сервере `init` создаёт
их от имени суперпользователя `postgres` (другой — `--superuser`): пароль берётся из `PGPASSWORD`
или запрашивается в терминале. Повторный запуск только обновляет пароль роли.

**2. Таблицы** — часть приложения, пакет `sales_analytics.storage`:

```bash
python -m sales_analytics.storage create --yes
```

Таблицы пересоздаются, существующие данные удаляются, поэтому нужен флаг `--yes`.

| Файл в `src/sales_analytics/storage/` | Назначение |
|---|---|
| `sql/tables.sql` | таблицы, индексы и представления |
| `schema.py` | `create_tables()` |
| `postgres.py` | `connect()` — подключение к базе из кода: `from sales_analytics.storage import connect`; `create_database()` — роль и база |
| `entities.py` | датаклассы `Branch`, `Product` и `DemandData` — данные для прогноза спроса |
| `repository.py` | `load_demand_data()` — чтение справочников, ассортимента, продаж и календаря из базы, `load_demand_data_csv()` — то же из датасета в CSV |
| `export.py` | `export_dataset()` — выгрузка всех таблиц в `data/`: `python -m sales_analytics.storage export` |

## Модель данных

| Группа | Таблицы |
|---|---|
| Справочники | `branches`, `categories`, `products`, `suppliers`, `customers`, `services` |
| Внешние данные | `calendar` — производственный календарь, `metal_price_index` — индекс цен на металлопрокат |
| Цены | `price_history` — розничная и оптовая цена, действующая с `valid_from` |
| Продажи | `sales_orders`, `sales_order_lines`, `order_services` |
| Склад | `purchase_receipts(_lines)`, `stock_transfers(_lines)`, `stock_movements` |
| Аналитика | `v_sales`, `v_stock_on_hand`, `mv_daily_sales` |

- Количество в документах хранится в единицах товара (`m`, `pcs`, `sheet`, `roll`, `pack`, `kg`),
  `products.kg_per_unit` переводит его в килограммы. Длинномерный прокат продаётся целыми хлыстами
  (`stick_length_m`), некондиция — произвольной длины.
- `stock_movements` — регистр движения товаров: остаток на любую дату равен сумме `quantity`.
  Начальные остатки на дату ввода системы — движения типа `adjustment`.
- Анонимные розничные покупки хранятся с пустым `customer_id`. Имена физических лиц не хранятся.
- `mv_daily_sales` — продажи по дням, базам и позициям, основа для прогнозирования.
  После загрузки данных её нужно обновить: `REFRESH MATERIALIZED VIEW mv_daily_sales`.

## Почему так

### Модель учётной системы, а не таблица для обучения

В дипломной работе база состояла из одной таблицы `sales_data` с готовыми месячными итогами.
Здесь база повторяет устройство настоящей учётной системы: документы (заказы, приходные
накладные, перемещения) и справочники, из которых итоги собираются запросами.

Причина — данные для модели должны получаться так же, как на реальном предприятии. Агрегат
«продажи за неделю» в учётной системе нигде не хранится: его надо собрать из строк заказов,
отбросив отменённые, и решить, что считать началом ряда и закрытой неделей. Эти решения —
часть методики (см. [preprocessing.md](preprocessing.md)), и на готовой таблице их не было бы видно.
Кроме того, документы позволяют строить признаки, которых в итоговой таблице нет: остатки,
цены, сегменты клиентов, сроки поставки.

### PostgreSQL, а не MySQL

| Возможность | Зачем в проекте |
|---|---|
| материализованные представления | `mv_daily_sales` — 940 тыс. строк заказов, заранее собранные в дневные продажи. В MySQL их нет, пришлось бы поддерживать таблицу-копию вручную |
| `COPY ... TO STDOUT` | потоковая выгрузка таблиц в CSV без промежуточных файлов на сервере (`export.py`) |
| `jsonb` | атрибуты товаров разные: у трубы — диаметр и стенка, у листа — толщина и покрытие, у сетки — ячейка. Одна колонка `jsonb` вместо десятков колонок, пустых у большинства строк |
| `CHECK` | допустимые единицы, статусы, форматы баз, `quantity > 0` проверяются самой базой |
| транзакционный DDL | `create_tables()` пересоздаёт схему в одной транзакции: при ошибке в середине скрипта база остаётся прежней, а не наполовину удалённой |

Плюс PostgreSQL — свободная лицензия и официальный образ Docker, поэтому развернуть базу можно
одной командой.

### Документ: шапка и строки

Заказ, приходная накладная и перемещение хранятся в двух таблицах: шапка (база, клиент, время,
канал, статус) и строки (позиция, количество, цена). Это нормализация до третьей нормальной
формы: данные заказа не повторяются в каждой строке, а у строки один первичный ключ
(`order_id`, `line_no`).

Цена и скидка хранятся в строке заказа, а не берутся из `price_history`, потому что документ
фиксирует сделку на момент продажи. Прайс-лист потом меняется, а проданное по старой цене
остаётся проданным по старой цене.

### Регистр движения товаров

Остаток не хранится как отдельное число, которое обновляется при каждой операции. Вместо этого
каждый документ записывает движения в `stock_movements` — приход со знаком плюс, расход
со знаком минус, — а остаток на любую дату равен сумме движений до неё. Так устроены регистры
накопления в учётных системах, например в 1С.

- **Остаток нельзя рассинхронизировать.** Нет второй копии данных, которая могла бы разойтись
  с документами.
- **Известен остаток на любую дату в прошлом**, а не только текущий. Для прогноза это главное:
  только так можно узнать, был ли товар на складе в неделю, когда продажи были нулевыми, —
  то есть отличить отсутствие спроса от дефицита.
- **Плата за это — суммирование при каждом запросе остатка.** Его ускоряет индекс
  (`branch_id`, `product_id`, `moved_on`).

Из того же регистра берётся начало ряда для прогноза — первое движение позиции по базе.

### Количество в единицах товара

Документы хранят то, что указано в документе: 12 хлыстов арматуры, 3 листа, 2 упаковки
саморезов. Вес — производная величина: `quantity × kg_per_unit`. Если хранить вес, пришлось бы
пересчитывать все документы при уточнении веса единицы, а продажа «целыми хлыстами» перестала бы
быть видна.

### Представления

- `v_sales` — **одно место, где определено, что такое продажа**: строки заказов со статусом
  `completed`, с весом и сегментом клиента. Все запросы аналитики идут через него, и правило
  нельзя случайно применить по-разному.
- `mv_daily_sales` — дневные продажи по базам и позициям, источник данных для прогноза.
  Материализовано, потому что агрегация почти миллиона строк при каждом обучении не нужна:
  данные меняются раз в день, а читаются многократно. Уникальный индекс позволяет обновлять
  его командой `REFRESH MATERIALIZED VIEW CONCURRENTLY`, не блокируя чтение.

### Персональные данные

Анонимные розничные покупки хранятся с пустым `customer_id`, имена физических лиц
не хранятся вообще: для прогноза они не нужны, а хранение персональных данных требует
соблюдения 152-ФЗ. Достаточно сегмента и города клиента.

### Производственный календарь — таблица

Рабочие дни в России нельзя вычислить по правилу: праздники переносятся ежегодным
постановлением правительства. Поэтому календарь — таблица, а не функция, и при отсутствии
данных за пределами её периода рабочими считаются дни с понедельника по пятницу.
